a · How an app switches its icon, and what your phone does

The only way: the icon belongs to whichever part of the app says "start me from the launcher". To offer more than one icon, Filet declares an activity-alias per icon for the same screen. Switching turns the new one on and the old one off with PackageManager.setComponentEnabledSetting(…, DONT_KILL_APP). Android has no "set my icon" call.

Each design in each colour is its own alias. Eight designs in four colours makes 32 aliases per build, only one of them on at a time. Each needs its own launcher icon files. The build makes them from the same art, so none is drawn by hand. Filet Debug keeps its amber in every design, so you can always tell the two apart; only the design switches there (my proposal). Ember sits close to that amber: an Ember Filet beside Filet Debug would look alike.

The icon moves. The launcher sees one entry vanish and another appear. Stock Android takes the old icon off the home screen and puts the new one only in the app list. Launchers with no app list, like Huawei's standard layout, usually put a new entry at the end of the last home screen. Either way it leaves its spot, on every switch, not just the first. Firefox hit exactly this: changing its launcher entry made people's home-screen icons vanish (Mozilla bug 1268455; also this write-up).

Does Filet get closed? With DONT_KILL_APP, Android's package manager doesn't stop the app, and the open screen belongs to the real activity, not the alias being turned off. But developers report some phones closing the app anyway, and one guide says switching closes it. Unknown on the test phone: device check 1.

The launcher can take a few seconds to show the change. Filet Debug is a separate app with its own colours, and switches on its own.

b · The risk: your pinned shortcuts

They're tied to an activity. A shortcut pinned without naming an activity is given the app's first launcher activity at the moment it's pinned. That's every shortcut you've pinned, tied to MainActivity today:

// ShortcutRequestPinProcessor.requestPinShortcutLocked (Android 12)
if (inShortcut.getActivity() == null) {
    inShortcut.setActivity(mService.injectGetDefaultMainActivity(
            inShortcut.getPackage(), inShortcut.getUserId()));
}

What Android does when that activity stops being a launcher entry: it rescans the app (ShortcutService.handlePackageChanged → rescanPackageIfNeeded(…, forceRescan = true)). The rescan turns off only dynamic shortcuts whose activity is gone:

// ShortcutPackage.rescanPackage (Android 12)
// Disable dynamic shortcuts whose target activity is gone.
if (si.isDynamic()) {
    ... else if (!s.injectIsMainActivity(si.getActivity(), getPackageUserId())) {
        disableDynamicWithId(si.getId(), false, ShortcutInfo.DISABLED_REASON_APP_CHANGED)

The shortcuts you pin with the shortcut sheet (files, folders, tabs, actions, scripts) aren't dynamic, so Android leaves them on. The exception is the four entries in the menu when you hold Filet's icon, which are dynamic. If you ever dragged one onto the home screen, a switch greys it out ("app changed"), and the menu itself empties until Filet publishes it again. The switch must republish it straight away.

Settled, and not: what Android does is settled; I read it from the Android 12 source, your phone's version (ShortcutPackage, ShortcutRequestPinProcessor, ShortcutService). What Huawei's launcher draws is not: a launcher could file shortcuts under the app's own entry and drop them when it changes. That's device check 2.

No way round, if it does: pointing shortcuts at a part of Filet that never switches doesn't work. Android only accepts an activity that is itself a launcher entry (fixUpIncomingShortcutInfo: "Cannot publish shortcut: activity … is not main activity"), and an always-on one would be a third Filet icon in your app list. If your launcher drops them, a switch costs your pinned shortcuts. Then it's either a warning before the switch, or no App icon row at all.

The one-time move A, left to the orchestrator, 2026-11-14

Today the launcher entry is MainActivity itself, which also takes every "Open with Filet" and is what Filet opens internally, so it can never be turned off. Before any switch is possible, the entry has to move.

A, taken: MainActivity stops being a launcher entry, and the aliases take its place. The cost: on the update that brings this, your home-screen Filet icon is re-placed once, just as a switch would.

B, not taken: renaming the screen's class would keep that update from moving the icon, but every switch after it moves the icon anyway, and any "Always open with Filet" you set would reset once.

Rules the build must keep

  • Two stores, never one. The setting holds Tabs, Files and folders (folders, files), Gallery (folders, files) and Shortcuts tab. The folder record (FolderStyles, by file id) holds the emblem, colour, cover and Show emblem. Turning a look on or off writes only the setting, and Change icon writes only the folder record. A test switches every look on and back off and checks that every folder record is byte-for-byte unchanged.
  • Drawn when drawn. No icon is stored. Every icon is drawn from the place's look plus the folder's record, so switching back to Drawn brings back exactly what was there, emblem included, with no restart.
  • Each place on its own. Changing one place's choice changes only that place. Home never reads the setting, and neither do the launcher icons, home-screen shortcuts, or the bar and its preview.
  • Pictures stay pictures. Thumbnails, video frames, album art and app icons look the same in every look. A choice changes only what has no picture of its own.
  • Legacy keeps its old rules: up to three pictures from inside, fanned, none below 22dp, and none for a folder with no pictures. A cover chosen with "Use a photo from inside" stands in the middle of the fan. Legacy outline shows no pictures and no cover.
  • Export carries the setting with the other Appearance settings, and the folder records travel as they already do. It carries the app icon too, and Import asks "Also use this app icon?" before switching.decided, 2026-11-14
  • Change icon follows the lists. Its preview draws the folder in the look the lists use, so what you pick is what you get.
  • Gallery is all six category galleries plus the grid views.
  • Home's category buttons stay drawn whatever Gallery says, so IconStyle's note that Home never provides a style stays true.
  • An emblem shows only when the folder has one, its Show emblem is on, and the place's Folders choice isn't Legacy outline. Nothing that hides an emblem clears it.
  • Each place hides by its own Folders choice. Lists follow Files and folders › Folders, the grids follow Gallery › Folders. Change icon follows the lists, as its preview does, so its tick greys when Files and folders › Folders is Legacy outline.
  • Show emblem is per folder, on by default, and kept in the folder's record. Greyed, it shows its saved value and the line Legacy outline shows no emblems. Yours is kept. Apply on several folders sets it on all of them.
  • The shortcut sheet's "Same as the folder" writes the same record, so it gets the same tick. It's never greyed there: home-screen icons don't follow Legacy icons.
  • Tabs: a Legacy folder chip is the plain outline, never an emblem. A Drawn chip follows its folder, Show emblem included.
  • App icon switches republish the hold menu straight away. Every design and colour is an alias the build generates, and Filet Debug keeps its amber.
  • Default: every place on Drawn, which is today's app.
